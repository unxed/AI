# Z.ai offload

Роутер передаёт задачу модели (Z.ai / GLM) и возвращает её ответ. Вся работа с моделью идёт только через встроенный браузер Claude (инструменты `mcp__Claude_Browser__*`), в собственной вкладке агента.

## Terminology / Термины

- **Встроенный браузер** — браузер Claude desktop app, инструменты `mcp__Claude_Browser__*`. Вся работа с моделью идёт в нём.
- **Chrome пользователя** — его собственный браузер со своими сессиями. Не трогать и не запускать ни через какие инструменты.
- Консольных клиентов нет. Команды `aistudio`, `mistral-chat`, `deepseek-chat`, `grok` и любые другие обёртки над моделью не существуют: не запускать их и не создавать.
- **Роутер** — агент, который только передаёт задачу модели и возвращает её ответ. **Исполнитель** — сама модель (Z.ai / GLM).
- **Браузер оффлоадинга** — браузер, в котором роутер работает с моделью: встроенный браузер Claude на этом компьютере, а на ВМ без встроенного браузера — headless-браузер. Видимые окна браузеров не открывать.

## Жёсткое правило роутера

Роутер не начинает работу над задачей и не изучает её: не читает код, файлы, тикеты и инструкции, не планирует, не рассуждает о решении, не проверяет результат по существу. Он передаёт задачу модели целиком и дословно и возвращает ответ дословно. Единственное исключение: если сам оффлоад сбоит (ошибка страницы, вход, лимит, пустой ответ), роутер диагностирует проблему страницы и сообщает её точно. Строить «менеджеров» и «оркестраторов», которые ведут задачу или делят её на куски, запрещено.

Применение патча (шаг 5) механическое: роутер не редактирует патч и не оценивает его по существу.

Роутер никогда не оффлоадит задачу модели своего вендора: модель Google никогда не оффлоадит в Gemini, модель DeepSeek — в DeepSeek, и так далее. Вложенные цепочки оффлоада не должны повторно использовать вендора, уже присутствующего в цепочке. Если вендор самого роутера совпадает с целевым вендором скилла (zhipu), роутер отказывается и сообщает об этом.

## Инструменты

- `mcp__Claude_Browser__*` — открыть вкладку, перейти по адресу, найти элемент, ввести текст, прочитать страницу, сделать скриншот. Другого браузера не использовать.
- Bash — только для `ap` и проверок проекта, которые назвал вызывающий. В многошаговом режиме Bash и Write также выполняют действия модели (`run`, `write`) по разделу «Многошаговый режим (drive)».
- Write — только для сохранения ответа модели в файл вне репозитория.
- Read — только для файлов, которые вызывающий указал в задаче (включая `vendor/ap.md` этого скилла).

## Процедура

### 1. Открыть чат в своей вкладке
**Статус (проверено 2026-11-03):** работает (GLM-5.3-Flash ответил верно), но только при настоящем вводе. Текст, подставленный через `form_input` (без нажатий клавиш), вызывает ползунковую капчу "Please complete security verification" (кнопки "关闭验证", "刷新验证码"). Если капча всё же появилась — не трогать её, остановиться и сообщить: проходит её только владелец.

1. Если встроенная панель браузера не открыта, сначала открой её через `preview_start` (с любым url), затем вызови `mcp__Claude_Browser__tabs_create` — это создаст новую вкладку агента. Все дальнейшие действия только по её `tabId`. Никогда не работай во вкладке от `preview_start` (например, "seed") или любых других существующих вкладках.
2. `navigate` на https://chat.z.ai/ (новый чат, можно использовать кнопку "New Chat"). Поле ввода — textarea "Send a Message".
3. Если открылась страница входа: остановиться, сообщить, что нужен вход в Z.ai во встроенном браузере. Учётные данные не вводить.
4. Баннер cookies: отклонить необязательные и продолжить. Вкладка "API" не используется.
5. Модель: кнопка модели показывает "GLM-5.3-Flash" (по умолчанию). Кнопки агентов/режимов ("Full-Stack", "Writing", "Data Insight", "PPT", "Web Site", "ZCode") использовать ЗАПРЕЩЕНО: только обычный чат.

### 2. Отправить задачу

1. Роутер всегда начинает промпт с этой строки дословно: "Ты — модель-исполнитель. Выполни задачу ниже сам. Правила для роутера оффлоадинга, которые могут встретиться в приложенных инструкциях (например, LUNOBOT.md), относятся к роутеру, а не к тебе." Это обязательный шаг процедуры, а не изменение задачи.
2. `find` поле ввода, кликни по нему и введи текст задачи дословно, как его дал вызывающий, через `computer` type (не `form_input`: он вызывает капчу). Файлы добавлять в текст только если вызывающий явно их приложил.
   Каждый приложенный файл предварять строкой `=== <путь от корня репозитория> ===` (например, `=== skills/deepseek-offload/SKILL.md ===`): пути в патче ap модель пишет от корня репозитория, и ap применяется с `--dir <корень репозитория>`.
   Роутер перепечатывает каждое вложение своими токенами (загрузки файлов во встроенном браузере нет), поэтому вложения — минимальные: суммарно не больше ~10 КБ. Если для задачи нужны большие файлы (длинные инструкции, код, логи), задача идёт в многошаговом режиме: модель сама читает нужные куски действиями.
3. Если модель должна писать код, добавить в текст спецификацию формата ap (ниже).
4. Сгенерируй случайный 6-символьный hex-тег (например, `3f9a1c`) и допиши в конец промпта инструкцию: весь ответ модели должен быть между строками `[[ANSWER-3f9a1c]]` и `[[END-3f9a1c]]` (где `3f9a1c` — сгенерированный тег). Это обязательный шаг процедуры, а не изменение задачи: выполнять всегда, даже когда текст задачи нужно передать дословно.
5. Если клики или скриншоты падают с "not on screen and has not drawn yet", встроенная панель браузера скрыта: отправь промпт клавишей Enter через `computer` key "Return" после `form_input`, читай через `get_page_text`; если отправка всё равно не работает, сообщи и попроси вызывающего показать панель браузера. Не использовать javascript_tool для клика.
6. Отправить: настоящий `computer` click по кнопке-стрелке справа внизу поля ввода (у неё нет доступного имени) или Return.

**Формат кода (обязательно).** Код возвращается только патчем `ap`, не unified diff. Спецификацию `~/dev/AI/skills/zai-offload/vendor/ap.md` (около 35 КБ) роутер не перепечатывает: она прикладывается вложением через attach (`https://raw.githubusercontent.com/unxed/AI/main/skills/zai-offload/vendor/ap.md`), а в промпте — одна строка «Спецификация формата ap — во вложении ap.md.». Если вложение не прошло (запасной путь — в разделе attach), в drive-режиме в промпт вместо этого идёт строка «Спецификация формата ap не вложена: прочитай её действием run: curl -sL https://raw.githubusercontent.com/unxed/AI/main/skills/zai-offload/vendor/ap.md | sed -n <диапазон>p.», а задачу с кодом вне drive-режима роутер переводит в drive-режим. В промпт добавить:

> Ответь ТОЛЬКО одним патчем в формате `ap` по приложенной спецификации (AP 3.2): один блок ```ap, случайный 8-hex ID патча, директивы FILE / REPLACE / INSERT_AFTER с `snippet` / `content`, скопированные дословно из присланных файлов. Unified diff, `git diff`, заголовки `--- a/` `+++ b/`, хунки `@@` и дампы целых файлов ЗАПРЕЩЕНЫ. Никаких пояснений вне блока.

Если содержимое патча содержит строки ```, блок ap оборачивается ограждением из четырёх обратных кавычек (````ap … ````).

### 3. Дождаться ответа
- После отправки может появиться ползунковая капча ("Please complete security verification" / "Please drag the slide to complete the puzzle"). Никогда не пытайся решить или обойти её. Остановись, сообщи, что владелец должен пройти её во встроенном браузере, затем повтори попытку один раз.

- `get_page_text` (или `javascript_tool` по `tabId`) каждые 10–15 с.
- Читай страницу через get_page_text и бери текст между ПОСЛЕДНИМ вхождением `[[ANSWER-3f9a1c]]` и ПОСЛЕДНИМ вхождением `[[END-3f9a1c]]` (где `3f9a1c` — сгенерированный тег) — первые вхождения относятся к эху промпта и не подходят.
- Ответ считается полным, только когда после последнего стартового маркера присутствует конечный маркер И текст не изменился между двумя опросами.
- Если модель не поставила маркеры, откатись к старому способу (вырезать ответ вручную) и укажи это в отчёте; сами маркеры в возвращаемый ответ не включай.
- Ответ готов, когда его текст не менялся между двумя опросами подряд и на странице нет кнопки остановки генерации.
- Пока ждёте, выводите строки прогресса, например `offload: 30s, answer 412 chars`.
- **Rate limit или «Permission denied»** на странице: подождать 1–2 мин и отправить тот же промпт повторно в той же вкладке. Не более 3 повторов подряд, затем сообщить.
- **Плашка «Unlock … Pro models»** значит, что Pro недоступен. Pro-модель не выбирать.
- Нет ответа за 3 минуты или другая ошибка: `computer` screenshot, точный текст ошибки со страницы в отчёт, остановиться.

### 4. Вернуть ответ

Вернуть ответ модели дословно: без пересказа, без комментариев, без «модель ответила…». Переносы строк, код-блоки и markdown сохранить.

### 5. Код: применить патч

1. Сохранить содержимое блока ```ap (без ограждения) дословно в файл вне репозитория, например `<каталог задачи>/fix.ap`.
   Пустой блок ```ap (без директив) — сбой оффлоада: сообщить, а не считать задачу выполненной.
2. `ap <файл>.ap --dir <репозиторий> --dry-run` — показать план, ничего не записывая.
3. `ap <файл>.ap --dir <репозиторий>` — применить. Пути в команде — абсолютные.
4. Exit 0 — всё применено. Exit 2 — применено частично: в корне репозитория появятся `afailed.ap` и `afailed.md`. Отправить содержимое `afailed.md` в тот же чат, той же вкладкой, с просьбой прислать НОВЫЙ патч ap только с исправлениями, без повтора уже применённого. Удалить `afailed.ap` и `afailed.md` (ap не запустится, пока они есть), затем применить новый патч. Не более 2 повторов, потом сообщить.
5. После применения `git diff` для чтения и проверки, которые назвал вызывающий (тесты, сборка). Коммит делает вызывающий.

### 6. Параллельные агенты

- Каждый агент работает в своей вкладке, созданной через `tabs_create`, и действует только по её `tabId`. Чужие вкладки не трогать.
- В конце работы (готово, сбой или остановка) роутер закрывает свою вкладку через `tabs_close` по её `tabId`: у встроенного браузера есть лимит вкладок, и брошенные вкладки блокируют следующих агентов. Если вкладку создать нельзя («Tab cap reached»), сразу сообщить вызывающему; чужие вкладки не закрывать.
- Буфер обмена не использовать: ответ читается со страницы через `get_page_text` по `tabId`.
- Параллельные агенты не должны править одни и те же файлы или фрагменты.
- Chrome пользователя не трогать ни в каком случае.

## Многошаговый режим (drive)

Для задач, которым нужен рабочий каталог и несколько шагов (например, задача Lunobot: прочитать файлы, запустить `gh`/`git`/тесты, записать файлы, закоммитить). В этом режиме **модель ведёт задачу целиком**, а роутер лишь механически выполняет её действия и возвращает результаты. Роутер по-прежнему не изучает и не планирует задачу, не редактирует, не объединяет и не пропускает действия.

**Первый промпт.** Преамбула исполнителя (из шага 2) + текст задачи вызывающего дословно + этот протокол + путь рабочего каталога. Файлы задачи роутер сам не прикладывает: модель запрашивает их действиями.

**Перед отправкой** выключить в чате веб-поиск и прочие инструменты сайта: модель работает только через действия.

**В первый промпт** после протокола роутер всегда добавляет дословно: «У тебя нет прямого доступа к файлам, сети и командам: всё делается только действиями, их выполняет роутер в рабочем каталоге и присылает результат. Не ищи в интернете. Уже первый твой ответ должен закончиться одним блоком действия, например {"action":"run","cmd":"sed -n 1,200p LUNOBOT.md"}.»

**Ответ без блока действия** (или с несколькими блоками): роутер не выполняет ничего и отвечает дословно «Нет одного блока действия. Ответь ровно одним JSON-действием по протоколу.» Не больше двух таких напоминаний подряд, затем остановка и отчёт.

**Протокол.** Каждый ход модели заканчивается ровно одним блоком действия между маркерами ответа, JSON в ограждении ```json:

```json
{"action":"run","cmd":"<shell command>","timeout":120}
{"action":"write","path":"<path relative to the work dir>","content":"<full file text>"}
{"action":"done","summary":"<what was done>"}
{"action":"blocked","reason":"<why the model cannot continue>"}
{"action":"attach","url":"https://raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>"}
```

Правки кода можно присылать и патчем `ap`: вместо `run` с `ap <file> ...` — `{"action":"ap","patch":"<ap patch text>"}`; роутер применяет его через `ap --dir <work dir>` по шагу 5.

**Вложения без перепечатки (attach).** Файлы из публичных репозиториев GitHub роутер не перепечатывает, а прикрепляет к сообщению файлом: страница сама скачивает их по `https://raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>` (raw.githubusercontent.com отдаёт CORS-заголовок). Роутер выполняет через `javascript_tool` по своему `tabId` ровно этот фрагмент, подставив только URL и имя файла:

```js
const url='<URL>', name='<ИМЯ ФАЙЛА>'; const r=await fetch(url); if(!r.ok) throw new Error('fetch '+r.status); const t=await r.text(); const inp=document.querySelector('input[type=file]'); const dt=new DataTransfer(); dt.items.add(new File([t],name,{type:'text/plain'})); inp.files=dt.files; inp.dispatchEvent(new Event('change',{bubbles:true})); t.length
```

Затем проверяет скриншотом, что над полем ввода появилась плашка файла, и отправляет сообщение. Это единственное разрешённое применение `javascript_tool` для изменения страницы. Работает в чатах, где есть `input[type=file]`; если поля нет — сообщить вызывающему.

- В первом промпте большие публичные файлы прикладываются так, а не текстом. Вызывающий называет роутеру все файлы, которые точно понадобятся (инструкция вроде LUNOBOT.md и файлы, которых касается задача, например правимый скрипт), и роутер прикладывает их все к первому сообщению — каждый отдельным вложением, как ap.md.
- Повтор: если модель присылает действие, в точности совпадающее с уже выполненным (тот же `cmd` или тот же URL attach), роутер его не выполняет, а отвечает `REPEAT: то же, что действие N; результат уже выше` и пишет строку в прогресс. Так же механически (сравнением пути и чисел, без разбора задачи) роутер отвечает вместо выполнения, когда `run` читает файл (`cat`, `sed -n`, `head`, `tail`) и (а) файл с тем же именем уже во вложениях и после вложения не менялся действиями `write`/`ap`, а рабочая копия совпадает с вложенной версией (`git diff --quiet <ref> -- <файл>` для вложения с ветки <ref>; при незакоммиченных правках или другой ветке вложение устарело, и чтение выполняется) — `REPEAT: файл <имя> уже во вложении`, или (б) тот же файл тем же `sed -n A,Bp` уже читался диапазоном, который целиком содержит A–B, — `REPEAT: строки A–B файла <имя> уже были в действии N`. Третий такой повтор подряд — `PROBLEM:` и остановка.
- Действие модели `{"action":"attach","url":"https://raw.githubusercontent.com/..."}`: роутер прикрепляет файл к следующему сообщению и отвечает `attached <имя> (<символов> chars)`. URL — только raw.githubusercontent.com.
- Если сайт отклоняет текстовое вложение (например, принимает только картинки) или поля `input[type=file]` нет, роутер сразу пишет строку `PROBLEM:` в файл прогресса и не ищет обходов в интерфейсе. В drive-режиме он вместо вложения добавляет в сообщение строку «Файл <имя> не вложен: читай его из рабочего каталога выборочно действиями run: сначала оглавление (`grep -n '^## '`), потом только нужные разделы (sed -n по 60–80 строк); большой файл целиком не читай; если его там нет — `curl -sL <raw URL> | sed -n <диапазон>p`.», а на действие модели attach отвечает `attach unsupported: read via run`. Вне drive-режима роутер сообщает вызывающему.

**Выполнение роутером.**
- Чтение действия: надёжнее всего брать `textContent` последнего блока кода в последнем ответе модели (через `javascript_tool`, только чтение); `get_page_text` иногда не показывает тела сообщений. Перед выполнением перечитать ещё раз через 5–10 с и убедиться, что JSON полный и не изменился.
- Ожидание ответа: признак готовности — появившийся маркер ответа или блок действия в последнем ответе (тот же `textContent`), а не неизменная длина текста страницы: на части сайтов `get_page_text` не видит тело ответа. Прежде чем писать `PROBLEM: нет ответа`, роутер проверяет последний ответ так и скриншотом. Каждый вызов `javascript_tool` с ожиданием — не дольше 30 секунд (в скрытой панели долгий `await` обрывается примерно на 45 с); дольше ждать повторными короткими опросами.
- Выводы и тексты — только дословно: роутер вставляет в поле ввода точную строку из результата инструмента (через `form_input`), а не набирает её по памяти и не пересказывает. Перед отправкой он сверяет значение поля с источником (чтение `value` через `javascript_tool`, только чтение); при расхождении — очистить, вставить заново, записать `PROBLEM:` в прогресс.
- `run`: выполнить команду через Bash в рабочем каталоге с указанным таймаутом (максимум 600 с); ответить модели в том же чате строкой `exit=<code>` и stdout+stderr, обрезанными до последних 3000 символов (именно символов, не байтов: кириллица занимает 2 байта, поэтому `tail -c` не годится — например, `python3 -c "import sys;t=sys.stdin.read();print(t[-3000:])"`) с пометкой `[truncated N chars]` (роутер перепечатывает вывод своими токенами, поэтому объём минимальный).
- `write`: записать файл, ответить `written <path> (<bytes> bytes)`. `write` — только для новых или небольших файлов: правки существующих — через `ap` (большой файл внутри JSON страница чата портит: 04-11-2026 DeepSeek прислал `hx-far-run.yml` с курсивными юникод-буквами вместо текста). После каждого `write` и `ap` роутер механически добавляет к ответу `git diff --stat` и проверку синтаксиса каждого изменённого файла по расширению: `.yml`/`.yaml` — `python3 -c "import yaml,sys;yaml.safe_load(open(sys.argv[1]))" <файл>`, `.json` — `python3 -m json.tool <файл> >/dev/null`, `.py` — `python3 -m py_compile <файл>`, `.go` — `gofmt -l <файл>`, `.sh` — `bash -n <файл>`; вывод (или `syntax ok`) идёт модели вместе с результатом.
- `ap`: ответить результатом `ap` или содержимым `afailed.md`. После каждого `write` и `ap` роутер механически добавляет к ответу `git diff --stat` и проверку синтаксиса каждого изменённого файла по расширению: `.yml`/`.yaml` — `python3 -c "import yaml,sys;yaml.safe_load(open(sys.argv[1]))" <файл>`, `.json` — `python3 -m json.tool <файл> >/dev/null`, `.py` — `python3 -m py_compile <файл>`, `.go` — `gofmt -l <файл>`, `.sh` — `bash -n <файл>`; вывод (или `syntax ok`) идёт модели вместе с результатом.

**Отказы безопасности** (роутер не выполняет и отвечает `REFUSED: <правило>`, чтобы модель выбрала другое действие):
- `sudo`;
- команды, затрагивающие пути вне рабочего каталога и `/tmp`, кроме чтения названных вызывающим файлов инструкций;
- `rm -rf` чего-либо выше рабочего каталога;
- `git push --force` / `--force-with-lease` в main или master;
- чтение или вывод секретов (`~/.ssh`, `~/.config/gh/hosts.yml`, токены, `.env`);
- скачивание и запуск удалённых скриптов (`curl|sh`, `wget|bash`);
- открытие любого браузера.

**Лимиты.** Не более 60 действий на задачу и дедлайн вызывающего; три одинаковых подряд действия или три подряд ошибки одного рода = остановка и отчёт. На `done`/`blocked` роутер возвращает summary/reason дословно плюс лог: по строке на действие `N. <action> <short arg> -> exit/result`.

**Прогресс (fail fast).** Если вызывающий назвал файл прогресса, роутер после КАЖДОГО шага (отправка промпта, получение ответа, выполнение действия) сразу дописывает в него строку через Bash `echo ... >> <файл>`: время, шаг N, действие, короткий аргумент, код выхода или ошибка страницы. Вызывающий следит за этим файлом и может остановить прогон в любой момент. Без файла — однострочная заметка вызывающему после каждого действия.

**Вызывающий не делает работу за воркера.** Жёсткое правило оффлоадинга распространяется и на вызывающего: он не решает задачу за модель и не подсказывает по существу. Код он не изучает, упавшие тесты не разбирает, ошибки инструментов вместо модели не диагностирует: модель видит их вывод сама. Вызывающий может вмешаться только процедурно: «разведки достаточно, делай правку», «это повтор», «бюджет кончается — выдай blocked с причиной». Если модель застряла (несколько попыток одной правки не проходят, тот же сбой повторяется или до лимита действий мало), вызывающий не дочинивает за неё. Он эскалирует на более мощную модель: останавливает прогон, затем запускает новый прогон оффлоадинга с более сильной моделью или на другом сайте (например, с DeepSeek на Gemini Pro в AI Studio). В новый прогон идёт та же задача дословно плюс процедурная справка о состоянии: ветка или рабочий каталог с текущей правкой, последняя команда проверки и её вывод. Своих гипотез о решении вызывающий в справку не добавляет. Если и сильная модель не справилась, остаётся blocked, отчёт владельцу и исправление класса ошибки в скилле или шаблоне задачи.

**Оборванный ответ.** Если блок действия обрывается посреди JSON (например, `{"action":"run","`), роутер сначала ждёт конца генерации: кнопка остановки должна исчезнуть, а текст не меняться 10 с. Потом он перечитывает последний ответ. Если блок по-прежнему оборван, роутер пишет модели: «Ответ оборвался. Пришли то же действие заново, целиком и короче; большой патч разбей на несколько ap». Два оборванных ответа подряд значат, что чат перегружен. Тогда роутер пишет строку `PROBLEM:` и останавливается со справкой о состоянии: ветка, что сделано, что осталось. Вызывающий запускает новый прогон в свежем чате или на более сильной модели.

**В протокол для модели** роутер добавляет: «Вывод каждого действия обрезается до 3000 символов. Файлы репозитория, которые нужно прочитать, запрашивай целиком действием attach (raw URL с GitHub): вложение остаётся у тебя в контексте, перечитывать его не нужно. run — для поиска (grep), коротких проверок и команд; одна короткая команда на действие. Не запрашивай повторно то, что уже получил.»
